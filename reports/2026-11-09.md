## 1. FastAPI

Expose a Python operation through a documented HTTP interface.

### What it does

Uses type hints, Starlette and Pydantic to define endpoints, validate request data and generate OpenAPI-based interactive documentation.

### Why we recommend it

Useful when another program needs a stable interface to an existing function. Defining inputs explicitly helps clients discover what to send without reading implementation code.

### How it could help you

1. Provide a small conversion function as a local endpoint for a separate UI.
2. Try valid and invalid request examples through generated API documentation.

### Who it fits and what to expect

MIT library for compatible Python on Windows, macOS and Linux. Needs a server process and framework dependencies, not a GPU; hosting, databases and external API use cost separately. Not a complete application or deployment. Authentication, resource limits and business rules still require design; async endpoints do not automatically speed CPU-heavy work.

### A small first step

20–30 minutes: follow https://fastapi.tiangolo.com/tutorial/ to create one local read-only endpoint. Inspect /docs and compare one valid input with an invalid one. Stop the development server afterward; leave deployment and model integration for a separate exercise.

## 2. Pydantic

State the expected shape of incoming data and inspect failures.

### What it does

Uses Python type hints and models to validate input and create typed objects. Its README demonstrates conversion of compatible values, so validation is not the same as refusing every differing input type.

### Why we recommend it

Recommended at a boundary where configuration or request data becomes internal state. A declared model makes assumptions visible; domain truth still needs explicit rules.

### How it could help you

1. Validate a fabricated settings object before a script uses it.
2. Check missing fields and invalid values in mock request records.

### Who it fits and what to expect

MIT local Python library, usable on major OSs with compatible packages and compiled core wheels. No service or GPU is necessary; Logfire is a separate product. V1/V2 have breaking differences. Coercion may accept inputs you expected to reject, so review strictness; valid structure does not prove factual correctness.

### A small first step

15–25 minutes: follow the documentation linked by the README, define a two-field BaseModel and compare valid, missing and invalid inputs. Inspect the parsed values and errors, then compare strict behavior for one field. Use fabricated data and match examples to your installed major version.

## 3. pytest

Turn a concrete expected behavior into a repeatable check.

### What it does

Discovers test functions, reports plain-assert failures and offers fixtures for shared test resources. It also supports existing unittest suites and optional plugins.

### Why we recommend it

Recommended for a bug or behavior that matters enough to preserve. A small example with a known expected result is easier to assess than a large suite mirroring implementation.

### How it could help you

1. Record a regression where a parser previously mishandled an empty value.
2. Use a temporary test fixture for a small file-reading function.

### Who it fits and what to expect

MIT framework; README lists Python 3.10+ or PyPy3. Runs locally on compatible Windows, macOS and Linux, with CPU/time costs determined by the tested code. No GPU unless that code needs one. Not proof of completeness: tests only cover selected cases, and plugins or test imports can execute code.

### A small first step

15–25 minutes: follow https://docs.pytest.org/en/stable/getting-started.html in a disposable environment. Write two small tests with manually known results, deliberately make one fail, inspect the failure, then correct the expectation or function as appropriate. Do not add a plugin until a real need appears.

## 4. Ruff

Check common code issues and formatting with one tool.

### What it does

A Rust-based Python linter and formatter with pyproject.toml configuration, editor integration, caching and optional fixes. Rule coverage is selectable; linting and formatting are distinct operations.

### Why we recommend it

Recommended when repeated style and simple static issues distract from code review. Start with reporting, then inspect any changes before enabling automatic fixes.

### How it could help you

1. Find an unused import in a small script.
2. Check whether a changed file matches the project's formatting policy before submitting it.

### Who it fits and what to expect

MIT; binaries and Python-package installation on supported Windows, macOS and Linux systems. Needs disk for the executable/cache, no GPU or hosted service. Not a type checker, test runner or logic verifier. Formatting and fixes can change files; rule choices should match the project. No speed benchmark was run for this report.

### A small first step

15–20 minutes after installation: follow https://docs.astral.sh/ruff/ and use ruff check plus ruff format --check on a disposable file. Read the diagnostic, fix one issue manually, then inspect the diff. Introduce automatic fixes only after understanding the selected rule.

## 5. pre-commit

Keep a small chosen set of checks close to the commit workflow.

### What it does

Runs configured hooks and manages their environments. Documentation at https://pre-commit.com/ explains setup and manual execution. It coordinates checks; it does not decide which policies suit a project.

### Why we recommend it

Recommended when an already useful check is easy to forget. Begin with one check and add others only when the team understands their purpose.

### How it could help you

1. Run a selected YAML check before reviewing a configuration change.
2. Apply the same pinned hook configuration to a small repository's contributors.

### Who it fits and what to expect

MIT framework for compatible Python/Git environments on major OSs. Hook runtimes, caches and first setup can need network/disk/time; service offerings are separate. Not a substitute for CI or review. Hooks execute selected code and may modify files; pinned revisions and inspected diffs matter.

### A small first step

20–30 minutes: follow https://pre-commit.com/ in a disposable Git repository, configure one reviewed hook at a fixed revision and run it manually. Compare a valid file with a deliberately invalid test copy and inspect changes. Install the Git hook only after the manual run behaves as expected.
