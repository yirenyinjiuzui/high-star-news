## Where to start today

Choose by the output you need: Pandoc for another editable format, Typst for a typeset PDF, Docling for extracting data from an existing PDF, Paperless-ngx for a permanent searchable archive, or Mermaid for a small diagram in your docs. If you only have one file to process, start with that file and the tool for its specific task.

## 1. Pandoc

Turn a structured document into another format from the command line.

### What it does

Pandoc reads a document into a common structure and writes it in a target format. It supports conversions such as Markdown to DOCX or HTML and DOCX to Markdown. Its Markdown dialect supports tables, footnotes and citations. PDF output uses a separate engine, with setup varying by the route you choose.

### Why we recommend it

Use it when one source needs to serve several readers or publishing systems. Maintaining one Markdown file can make revisions easier to track while still giving someone an editable Word copy. Check one representative document before committing to a batch conversion.

### How it could help you

1. Keep a project handout in Markdown and generate DOCX for reviewers who prefer Word. Check headings, links and the image caption in the result.
2. Convert a copy of a legacy Word guide to Markdown for a documentation repository. Compare the original and output to identify tables or callouts that need repair.

### Who it fits and what to expect

Fits readers comfortable with a terminal and simple text files. If exact Word layout or tracked review is central, keep the original editing workflow. Local CLI builds are available for Windows, macOS and Linux; plain DOCX/HTML conversion needs no hosted service. The README says GPL v2 or later; check separate terms for templates, fonts and PDF engines. Complex tables, custom styling and page margins may not survive conversion.

### A small first step

15–25 minutes after installation: create notes.md with two headings, a link and a small table. Run `pandoc notes.md -o notes.docx` and `pandoc notes.md -s -o notes.html`. Compare structure in both outputs. Leave PDF and complicated layouts for a second test. Official guide: https://pandoc.org/MANUAL.html .

## 2. Typst

Write a document as text and compile it into a designed PDF.

### What it does

Typst combines markup for headings, lists and equations with rules and functions for styling. The CLI compiles local .typ files and can rebuild when a source file changes. It can use additional font directories and supports bibliographies, useful when documents include formulas and citations.

### Why we recommend it

Try it when your recurring output is a printable PDF and you want to reuse page and heading styles. A small template can keep the layout consistent between editions while you revise the content in a text editor.

### How it could help you

1. Build a one-page formula sheet with numbered sections and equations, then change the page margins once to see how the whole page reflows.
2. Make a reusable two-page report with the same heading style and a bibliography; edit one reference and regenerate the PDF before sharing it.

### Who it fits and what to expect

Fits people willing to learn lightweight markup; may not suit a journal that mandates a specific LaTeX template or collaborators who need editable DOCX. The Apache-2.0 CLI has releases for Windows, macOS and Linux. It needs the binary, relevant fonts and any template packages; hosted collaboration plans and third-party font or package terms are separate. Font substitution and package versions can change the result, so inspect the exported PDF.

### A small first step

15–25 minutes: create a .typ file with a heading, list and one equation. Run `typst compile sample.typ`, add numbered headings, and compile again. If writing in Chinese, include a Chinese line and check that your installed font covers it. Official docs: https://typst.app/docs/ .

## 3. Docling

Extract document content into Markdown or structured data for later processing.

### What it does

Docling parses documents such as PDF and DOCX, and its PDF pipeline can identify layout, reading order and table structure. OCR handles image-based input, and the CLI and Python library can export Markdown or structured formats such as JSON. Local execution is supported; some configurations use different models or services.

### Why we recommend it

Recommended when copying text or extracting a table by hand is the bottleneck. It helps prepare material for search or analysis, and gives you output you can inspect before passing it to an AI system.

### How it could help you

1. Extract a two-column technical article, then compare the order of headings and paragraphs against the PDF before using the text for search.
2. Convert a public PDF with a table, inspect merged headers, units and five cells against the source, and decide whether automated extraction is dependable enough for similar documents.

### Who it fits and what to expect

Fits readers comfortable with Python or a CLI. Less suitable for perfect visual reproduction or unattended extraction of critical figures. The README lists Python 3.10+ on Windows, macOS and Linux. Code is MIT; model licenses vary. Installations can need model downloads and appreciable RAM, disk and CPU time. GPU needs depend on the pipeline; optional remote services may charge. Scans, complex layout and OCR can introduce errors; verify values and reading order.

### A small first step

15–30 minutes once installed and models are ready: choose a short public PDF or a local sample without private data, run `docling sample.pdf`, then compare the Markdown with three headings and a table in the original. Decide whether the misses are acceptable before processing a folder. Official docs: https://docling-project.github.io/docling/ .

## 4. Paperless-ngx

Make scanned documents searchable and organize them in a self-hosted web library.

### What it does

Paperless-ngx imports documents, runs OCR, indexes full text, and lets you organize the archive with tags, correspondents and document types. The docs describe storing an archival PDF/A alongside the original. Its default workflow is useful for keeping and finding documents over time.

### Why we recommend it

Recommended when finding a specific phrase or sender inside older scans is harder than adding a file. It puts text search and filters in one place. The benefit comes from consistent intake and maintenance; decide on a backup plan before replacing any existing archive.

### How it could help you

1. Import mock receipts with inconsistent filenames, tag them by category, then find one by a phrase inside the scan rather than by filename.
2. Create a saved view for example notices of one type, filter by sender, and compare the scan with its OCR text before relying on the index.

### Who it fits and what to expect

Fits households or teams able to manage a server, storage and backups; a folder and desktop search may be easier for a handful of PDFs. The GPL-3.0 project documents Docker Compose and a browser interface. Budget for host storage, backups and OCR CPU/RAM; optional external OCR or AI services can cost money and may process data remotely. OCR can miss words; keep originals, configure access, and test restores. A running service alone does not protect against disk loss.

### A small first step

15–25 minutes: explore the demo linked by the official README using only existing demo data, or import two fabricated scans in your own test instance. Try a text search and tag filter, open the original, then read the setup and backup guidance before a real import. Official docs: https://docs.paperless-ngx.com/ .

## 5. Mermaid

Describe flows and interactions in text that can be rendered alongside documentation.

### What it does

Mermaid is a JavaScript renderer for diagrams written with a Markdown-inspired syntax. It supports flowcharts, sequence diagrams and more. GitHub renders supported Mermaid blocks in Markdown, and the project links a live editor for prototyping. Diagrams are stored as text, so their changes can be reviewed as diffs.

### Why we recommend it

Use it for small diagrams that should stay close to the instructions or code they explain. A reviewer can inspect changes to a step or arrow without opening a separate design file. A good diagram still needs correct labels and a clear scope.

### How it could help you

1. Add a three-step document approval flow to a README and change one branch when the process changes. Check that the written instructions and arrows agree.
2. Draw a short sequence for an app request and an error response, then use it during a handoff to identify which component should handle the failure.

### Who it fits and what to expect

Fits people who prefer editing labels and relationships as text. Detailed print layouts, pixel-specific placement and very large diagrams may be better in a visual tool. The core code is MIT; supported hosts can render it in a browser, while embedding requires a compatible JavaScript environment. Hosted products may have separate terms. Rendering and feature support vary by host/version, so verify the target viewer. Avoid putting private workflow details into a shared editor or URL.

### A small first step

15–25 minutes: use a harmless example in a supported Markdown preview or the editor linked by the README. Start with `flowchart LR` and `A --> B`, then add a decision and label both exits. Check how the actual destination renders it before sharing. Official docs: https://mermaid.ai/open-source/ .
