## 1. Lazygit

A terminal interface for reviewing and staging Git changes.

### What it does

Shows files, diffs, branches and commits, with hunk/line staging and interactive history operations. The interface exposes Git operations rather than replacing the underlying repository.

### Why we recommend it

Recommended when reviewing a mixed working tree is cumbersome. Selecting a small, coherent change can make commits easier to understand.

### How it could help you

1. Separate documentation edits from code edits before committing.
2. Compare two commits while tracing when behavior changed.

### Who it fits and what to expect

MIT; free binaries for Windows, macOS and Linux, with Git and a compatible terminal required. No GPU or hosted service needed. Not a substitute for understanding Git. Reset and rebase operations can discard changes or rewrite history; undo does not cover every working-tree action.

### A small first step

20–30 minutes in a disposable local Git repository: edit two files, launch lazygit, inspect diffs, stage one hunk and make one local commit. Compare the result with git status. Leave reset, rebase and remote push for later. Follow the README basics tutorial.

## 2. Lazydocker

See container state, logs and resource graphs in one terminal.

### What it does

Offers a terminal UI for Docker and optional Compose services, including log viewing, metrics, image layers and lifecycle actions.

### Why we recommend it

Useful when checking several local services otherwise requires many terminals. Keeping status and logs together helps identify which service needs closer investigation.

### How it could help you

1. Select a failed demo service and inspect its logs beside its state.
2. Compare resource graphs for two development containers before changing their settings.

### Who it fits and what to expect

MIT free client for Linux, macOS and Windows. Requires a compatible running Docker engine and access to it; current README specifies Docker 29.0.0+, with Compose optional. Engine/Desktop licensing, container images and compute costs are separate. Not useful without containers. Restart, remove and prune actions can disrupt services or delete data; resource graphs do not establish root cause.

### A small first step

15–25 minutes with an existing disposable Docker environment: run lazydocker, inspect a container's state, logs and image layers, then exit without lifecycle actions. Check README requirements against your installed engine before setup; this report does not provision a container environment.

## 3. btop

Inspect CPU, memory, disk, network and processes together.

### What it does

A C++ terminal resource monitor with graphs, a process list and keyboard/mouse navigation. GPU coverage depends on platform, build options and available driver libraries.

### Why we recommend it

Recommended for a first look at a slow local task. Multiple resource views can suggest whether to investigate CPU, memory or I/O next, without claiming a definitive diagnosis.

### How it could help you

1. Watch memory and CPU while a small data conversion runs.
2. Compare idle network and disk activity with activity during a file copy.

### Who it fits and what to expect

Apache-2.0 free software for Linux, macOS and supported BSD systems; native Windows is a separate btop4win project. Needs a compatible terminal, fonts and OS metrics access. No AI model needed. GPU monitoring is not universal. Not a long-term telemetry archive, and WSL observations describe that environment rather than all Windows activity.

### A small first step

15–20 minutes after installing the appropriate package: run btop, identify CPU and memory panels, sort the process list, and compare idle readings with a harmless file copy. Do not terminate processes during this exercise. Read the README prerequisites if symbols or graphs render incorrectly.

## 4. zoxide

Jump to frequently visited directories using a short name.

### What it does

Remembers visited directories and ranks matches for its z command. Multiple keywords narrow matches; optional interactive selection uses fzf. Shell initialization connects directory tracking to normal navigation.

### Why we recommend it

Recommended for repeatedly switching between deeply nested project folders. It shortens navigation once your own directory history has useful entries.

### How it could help you

1. Move between a report folder and a source folder using distinct keywords.
2. Disambiguate two similarly named projects with a second directory keyword.

### Who it fits and what to expect

MIT free binary for Windows, macOS and Linux; supports PowerShell and major Unix shells. Needs shell initialization and a small local directory database; fzf is optional for interactive selection. Not a file-content search tool. Rankings may choose an unexpected path and a new database has little history; verify the current directory before subsequent commands.

### A small first step

15–25 minutes: follow the README setup for your actual shell, visit three disposable directories normally, then try z with one and two keywords. Print the current directory after each jump. If shell behavior changes unexpectedly, remove the initialization line to return to normal cd usage.

## 5. tldr-pages

Look up common command patterns before reading the full manual.

### What it does

A community-maintained Markdown collection of concise command examples. Official Python and Rust clients, a web client and downloadable PDFs provide different ways to read the pages; translations vary in coverage.

### Why we recommend it

Recommended as a starting point for an unfamiliar command or a forgotten option. Examples provide context quickly, while the command's own help remains important for version-specific details.

### How it could help you

1. Find a tar listing example before inspecting an archive.
2. Look up a git diff example, then compare its options with your installed Git help.

### Who it fits and what to expect

Pages use CC BY 4.0; clients have separate licenses and runtime requirements. Free reading via the linked web client or local client on supported platforms; downloaded caches/PDFs need disk space. Not every flag or platform is covered. Examples can differ from your command version; do not paste destructive commands without understanding their targets.

### A small first step

15–20 minutes: open the web client linked by the official README at https://tldr.inbrowser.app and read tar and git diff pages. Compare two examples with local --help or the relevant manual. Try only a read-only example on disposable files if desired, and check whether a translation covers the same options.
