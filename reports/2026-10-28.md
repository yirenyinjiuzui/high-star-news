## 1. jq

Ask precise questions of JSON without writing a full script.

### What it does

A lightweight command-line JSON processor for selecting fields, filtering arrays, mapping records, and transforming structured data. The README describes a portable C implementation with no runtime dependencies and links to standalone release executables. Its filters operate on JSON values, rather than treating the file as unstructured text.

### Why we recommend it

Recommend it when you repeatedly open an API response or exported JSON just to retrieve a few fields. A short saved filter makes the extraction explicit and repeatable. It is useful between a raw response and a spreadsheet or script, but it does not infer the meaning of fields or decide whether the source data is correct.

### How it could help you

1. Extract project names and star counts from an already-downloaded JSON export, instead of copying them one record at a time.
2. Filter a list of task records by an explicit status and inspect only the fields needed for a report; keep the original export for comparison.

### Who it fits and what to expect

Good for people comfortable with terminal commands and nested data. Official release binaries are the easiest starting point; choose the asset for your operating system. The README states MIT licensing for jq code, CC BY 3.0 for documentation, and separate ICU terms for included decNumber code. JSON input, filter syntax, shell quoting, and missing fields still need care. For substantial multi-step business logic, an ordinary script may be clearer.

### A small first step

Spend 20 minutes making a disposable sample.json with three objects in an items array, each with name and status fields. Try jq '.items[] | select(.status == "open") | .name' sample.json using quoting appropriate to your shell. Compare each output to the source and try a missing field. No command was executed for this report.

## 2. fd

Find filenames and directory entries with a small, readable command.

### What it does

A filesystem search utility with regular-expression and glob patterns, extension filters, and optional full-path matching. It searches recursively, uses smart-case behavior, and by default omits hidden entries and paths ignored by Git. It aims to cover common find-style tasks with opinionated defaults, not every advanced feature of find.

### Why we recommend it

Recommend it for the moment when you remember part of a filename or its extension but not the containing folder. It complements yesterday's ripgrep: fd locates entries by name or path, while ripgrep searches text inside files. That separation helps choose the right search instead of opening many folders manually.

### How it could help you

1. Locate all Markdown files whose names contain a topic across a notes directory, then open only the relevant candidates.
2. Find a configuration filename in a large checkout and inspect its full path before deciding which environment it belongs to.

### Who it fits and what to expect

Good for terminal users who navigate large directory trees. Official distributions cover common desktop platforms; choose the documented installation route. The repository provides MIT and Apache-2.0 license files. Default hidden/ignore filtering can omit a file you expect, and patterns are regex unless another mode is chosen. It is not a document-content or semantic search engine. Leave command-execution features out of the first trial.

### A small first step

Spend 15–20 minutes in a disposable directory with nested text and Markdown files. Compare fd -e md with fd -g '*.md', then search for a fragment of a known filename. Read the help for hidden and ignored entries and verify why a result is present or absent. Do not attach deletion or other bulk actions to the search.

## 3. bat

Read code and configuration with syntax context and visible changes.

### What it does

A cat-like terminal viewer with syntax highlighting, Git modification indicators, line numbers, and optional display of non-printable characters. It pages long interactive output, supports explicit language selection, and prints plain content when it detects redirected output. The README also describes integration with file finders and other tools.

### Why we recommend it

Recommend it when the file is already located but reading it in a terminal is awkward. Syntax cues and line numbers can help discuss a small configuration fragment or understand a code sample without opening a full editor. It is a viewer: highlighting does not validate syntax, execute code, or explain the author's intent.

### How it could help you

1. Read a configuration file beside an error message and use line numbers to identify the exact setting that needs further investigation.
2. Inspect a Markdown or source-code example in a checkout, with local Git modification indicators helping distinguish edited lines from the indexed version.

### Who it fits and what to expect

Useful for terminal-based text and code work; a regular editor may be better for navigation and editing large documents. Official packages are available on common desktop platforms. The repository supplies MIT and Apache-2.0 terms; the MIT file was checked. Some distributions call the executable batcat. Pager behavior, terminal colors, and display decorations can affect copying, so use documented plain-output options when needed. No default shell aliases need changing for a first test.

### A small first step

Use 15 minutes to compare bat README.md with bat --paging=never README.md in a test folder. Inspect a small JSON file with explicit syntax selection, then use bat -A on disposable text containing tabs. Confirm whether what you see is file content or a viewer decoration. These are proposed checks, not tests performed on the tool.

## 4. fzf

Narrow a long list interactively when you remember only fragments.

### What it does

A general-purpose fuzzy finder and terminal interface toolkit. It accepts candidate lists, lets you filter them interactively, and can support file selection, command-history browsing, previews, and custom menus. Official documentation lists binaries and package options, including Windows, plus integrations for several shells and editors.

### Why we recommend it

Recommend it for choosing among many already-available candidates instead of repeatedly retyping exact paths. It is especially useful once fd, a script, or another tool has produced the candidate list. It does not discover facts beyond its input, and fuzzy matching does not establish that the top result is the one you intended.

### How it could help you

1. Choose a notes filename from a generated list by typing a few memorable fragments, then inspect the selected path before opening it.
2. Browse a prepared list of task names or project directories interactively, reducing manual scrolling without changing any files.

### Who it fits and what to expect

Best for people who already work in terminals. MIT-licensed and free, with standalone binaries for a basic trial. Windows availability does not mean Bash/Zsh/Fish keybindings automatically apply to PowerShell. Shell integration is a separate setup step, and optional previews or execute bindings run configured commands. Start with a static, non-sensitive list and leave command-executing integrations unconfigured until you understand them.

### A small first step

In 20 minutes, create a three-line list of invented filenames and pipe it into fzf using your shell's normal text-input command. Filter, select, and cancel; confirm exactly what is returned. Then try a larger disposable list. Leave global keybindings and previews for a later decision. No shell integration was changed for this report.

## 5. delta

Make the difference between two versions easier to inspect.

### What it does

A pager for Git, diff, and grep output with syntax highlighting, word-level change emphasis, side-by-side layouts, line numbers, and navigation between sections. The README documents improved merge-conflict and blame displays. Package managers often call the package git-delta, while the executable is delta.

### Why we recommend it

Recommend it for the final review before a commit: clearly seeing what changed can reveal an accidental edit or missing context. It changes presentation, not the underlying patch or correctness of a change. Keep the plain Git output available when you need an unstyled reference or want to resolve ambiguity.

### How it could help you

1. Review a Markdown report edit and distinguish a small word change from a whole rewritten paragraph before publishing.
2. Inspect a code diff side by side, then check whether the surrounding logic supports the change rather than relying only on colored lines.

### Who it fits and what to expect

Useful for people already using Git in a terminal; occasional repository readers may prefer GitHub's built-in diff. MIT-licensed and free, with common desktop installation options in the official guidance. A compatible terminal and pager configuration matter. Colors can be misleading or inaccessible depending on theme, and narrow windows can make side-by-side review awkward. You can try a command-scoped pager without changing global Git settings.

### A small first step

Spend 20–30 minutes in a disposable Git repository with one small committed text file and an uncommitted edit. After installing through the documented channel, compare git --no-pager diff with git -c core.pager=delta diff. Verify the same changes appear in both. Keep this local to the command until you choose a layout; the report made no Git configuration changes.
