## 1. Dust

See which directories account for a chosen folder's disk use.

### What it does

A Rust disk-usage tool that presents large subdirectories and files with a hierarchical terminal view. Depth and item-count controls help focus the output without manually sorting a long listing.

### Why we recommend it

Recommended for deciding where to investigate space use before touching any files. A size overview is evidence of occupancy, not evidence that a directory is unnecessary.

### How it could help you

1. Inspect a disposable project folder to distinguish source files from generated output.
2. Compare two known folders' reported sizes before planning an archive.

### Who it fits and what to expect

Apache-2.0 tool with Windows, macOS and Linux installation options. Needs filesystem read access and time for scanning; some Windows builds need the documented runtime. No GPU required. Permissions, links and filesystem allocation can affect totals. It does not decide what can safely be deleted, and scans can cause substantial I/O.

### A small first step

15–20 minutes: read the official README and scan a small test directory with dust -n 10. Compare two entries with filesystem properties, then vary the depth. Keep the exercise observational; do not delete files based only on the largest bar.

## 2. eza

Read file types and metadata in a richer terminal listing.

### What it does

An ls alternative using colors and optional metadata such as symlink information and Git status. A single binary supports platform-specific installation; it changes the listing interface, not the underlying files.

### Why we recommend it

Useful when an ordinary directory listing hides the context needed to choose a file. Keep explicit commands while learning because its options are not identical to ls.

### How it could help you

1. Inspect a small repository's file types and Git-related listing information.
2. Compare a symlink entry with its target information before opening the file.

### Who it fits and what to expect

EUPL-1.2 project with Windows, macOS and Linux options. Requires a suitable terminal; fonts and platform metadata affect display. No GPU or service needed. Not a content searcher or disk-cleaning tool. Flags differ from ls, and recent repository activity is less frequent than other selections; the actual timestamp is recorded below.

### A small first step

15–20 minutes: follow the README/INSTALL.md, list a harmless test folder, then inspect a long listing and a repository listing using documented flags. Compare the output with file properties. Do not replace an existing ls alias until familiar with option differences.

## 3. Krokiet / Czkawka Core

Find candidate duplicate or unnecessary files for manual inspection.

### What it does

The repository now recommends the Krokiet GUI over its legacy Czkawka GTK GUI. It includes duplicate searches by name/size/hash, similar-image tools and other file checks; similarity and exact duplication are different tests.

### Why we recommend it

Recommended as an inspection aid for a known collection. It can identify candidates, while the decision about which copy matters still depends on content and context.

### How it could help you

1. Scan a fabricated folder containing deliberately duplicated test files.
2. Compare a resized image with its original to learn the difference between similarity and a matching hash.

### Who it fits and what to expect

Free multi-platform tools; licensing and requirements differ by component/frontend, so inspect the chosen package's terms. Krokiet binaries cover Windows 10/11, macOS and supported Linux; similar-video tools require ffmpeg. Scans/cache use disk, CPU and RAM. Deletion/metadata-removal features change files, and similar results are not necessarily redundant. Legacy GTK version 12.0 is its last release.

### A small first step

20–30 minutes: follow the repository's Krokiet README and use only disposable copied files. Scan exact duplicates, open candidate paths and compare contents without deleting. Try one similar-image case separately. Review export/cache behavior before scanning a real collection.

## 4. ImHex

Inspect a file's bytes and structured views rather than guessing from its extension.

### What it does

A hex editor with byte search, typed interpretations, bookmarks, patch management and a pattern language for describing file structures. It also links a web version and detailed documentation.

### Why we recommend it

Useful for learning a small known binary format or checking a header. It is a specialized inspection/editor tool; ordinary documents rarely need this level of detail.

### How it could help you

1. Inspect a fabricated file's first bytes and compare ASCII with hexadecimal.
2. View a harmless sample through different integer interpretations to understand endianness.

### Who it fits and what to expect

GPL-2.0 metadata; check package/component terms. Desktop builds and the linked browser version have different runtime/platform requirements; desktop graphics support and plugins may matter. No model needed. Editing bytes can corrupt files, and a pattern's interpretation is only as good as its definition. Not a tool that automatically proves a file is safe.

### A small first step

20–30 minutes: follow https://docs.werwolv.net/ with a tiny non-sensitive sample copied for the exercise. Search a known byte sequence, inspect an integer in both byte orders and add a bookmark. Avoid patch/save actions on the original; this report performs no artifact analysis.

## 5. PeaZip

Inspect and create archives through a cross-platform visual interface.

### What it does

An archive manager supporting many formats, split/join operations, archive browsing and hashing tools. Some formats can be read but not necessarily created by the same backend.

### Why we recommend it

Included below 10,000 stars because a cross-platform GUI and portable packages offer a concrete alternative to command-line archive workflows. This is an explicit exception, supported by recent repository activity.

### How it could help you

1. Create a small ZIP from disposable files and inspect its entries.
2. Check a downloaded public archive's file list before choosing a separate extraction folder.

### Who it fits and what to expect

LGPLv3 application with Windows, macOS, Linux and BSD packages; bundled backends have their own licenses and format capabilities. CPU/time and extra disk are needed for compression/extraction; no GPU. Not a guarantee that archive contents are harmless. Extraction paths, overwrites and unexpectedly large expanded sizes require review; encryption is not recovery without the password.

### A small first step

15–25 minutes: follow https://peazip.github.io and choose the official package for your OS. With three fabricated files, create a ZIP, inspect it, extract into a new disposable folder and compare content/counts. Do not overwrite original files or use unknown archives for the first exercise.
