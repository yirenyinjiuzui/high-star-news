## 1. Uptime Kuma

Check whether a service responds and inspect its recent availability.

### What it does

Self-hosted monitoring for HTTP, TCP, DNS, ping and other targets, with status pages, response charts and notification integrations. A check reports what its configured probe observed, not a complete diagnosis.

### Why we recommend it

Useful when you operate a small service and repeatedly check it manually. Start with one meaningful probe and decide what a failure should mean before adding alerts.

### How it could help you

1. Inspect a local demo service's HTTP response over time.
2. Compare a DNS check with an HTTP check to narrow a test outage.

### Who it fits and what to expect

MIT application with Docker deployment and documented non-Docker Linux/Windows options. Needs an always-running host, local persistent storage and backups; README excludes NFS storage. No GPU required. Hosting and notification providers can cost separately. The monitor can fail with the host it watches; a green probe does not prove every application function works.

### A small first step

20–30 minutes: read the official installation guide and inspect the temporary demo linked by the README. In an existing test instance add only a service you control, choose a modest interval and examine results without connecting notifications. Review retention and backup needs before normal use.

## 2. changedetection.io

Compare selected webpage content rather than repeatedly rereading it.

### What it does

Tracks page changes with differences, filters and selectors; JavaScript/browser interaction needs the appropriate fetcher. Optional AI summaries and triggers connect a separately configured model service.

### Why we recommend it

Recommended for a stable public page where a specific content change matters. Targeting one region can reduce navigation noise, but detected differences still need source verification.

### How it could help you

1. Track an allowed public project announcement section at a reasonable interval.
2. Compare revisions of a small test page you control while ignoring a changing timestamp.

### Who it fits and what to expect

Apache-2.0 project; browser UI needs a persistent server/container deployment and storage. Browser fetchers consume more CPU/RAM; hosted plans, proxies and model APIs have separate costs. No LLM is necessary for basic diffs. Dynamic pages, access limits and layout changes can produce failures or noise. Follow target-site rules and keep sensitive content out of external summarizers.

### A small first step

20–30 minutes: read the official README and fetcher requirements. In a ready test instance watch a harmless page you control, choose one selector, edit the page and inspect the raw diff. Leave browser steps, AI calls and outbound notifications unconfigured during this first check.

## 3. ntfy

Deliver a short event from a script to a subscribed device.

### What it does

An HTTP publish/subscribe notification service with phone and desktop clients, optional self-hosting and a hosted service with free and paid options. It transports an event generated elsewhere; it does not decide whether a task succeeded.

### Why we recommend it

Useful when an existing job already has a trustworthy completion or failure signal. A concise, deduplicated notification can surface that signal without copying logs full of private data.

### How it could help you

1. Send a harmless completion event from a test script to your own subscribed client.
2. Route one distinct failure type from a private test service instead of every routine log line.

### Who it fits and what to expect

Server metadata identifies Apache-2.0 licensing; client and provider terms should be checked separately. Needs network, a reachable server and a compatible web/mobile client. Self-hosting adds storage, authentication and updates. Provider limits, paid plans and platform delivery behavior vary. Topic names alone should not be treated as access control, and delivery is not guaranteed.

### A small first step

15–25 minutes: follow https://ntfy.sh/docs/ and first review authentication, access and retention. If you already have a private authorized test topic, send one fabricated message to your own device and inspect it. Do not use a public topic for secrets or assume the tutorial creates a private channel.

## 4. Homepage

Put known service links and selected status widgets on one page.

### What it does

A configurable application dashboard with bookmarks, search, service widgets and optional Docker discovery. YAML configuration and backend-proxied integrations connect the page to existing services.

### Why we recommend it

Recommended when the problem is locating and checking several services, rather than building a new monitoring engine. Keep the first page limited to links and one useful status signal.

### How it could help you

1. Group your own test-service links by task.
2. Inspect one supported service widget beside its canonical management link.

### Who it fits and what to expect

GPL-3.0 project; needs a compatible container/Node deployment, config storage and browser clients on common platforms. Server, backups and external widget APIs have separate costs. No GPU required. Proxying API keys does not make the dashboard safe to expose publicly: follow its authentication/TLS/host-header guidance. Docker integration is optional and grants additional access.

### A small first step

20–30 minutes: read https://gethomepage.dev/ and prepare a local-only test page with two harmless bookmarks. If already running, add one supported read-only widget and compare it with the original service. Avoid Docker socket discovery and public exposure until requirements and access controls are understood.

## 5. Glance

Read a chosen set of feeds and information widgets in a compact page.

### What it does

A configurable dashboard with RSS, video-channel and other information widgets, page layouts and themes. Distributed binaries and Docker options provide ways to run the server; YAML controls the content.

### Why we recommend it

Recommended when you want a small information overview rather than an application launcher. Selecting a few sources deliberately can be more useful than filling every available panel.

### How it could help you

1. Put two public RSS feeds beside a calendar for a focused reading start page.
2. Compare the dashboard's cached feed item with its original source before acting on it.

### Who it fits and what to expect

AGPL-3.0 project, with binaries for multiple OSs/architectures and a Docker image. Needs an always-running compatible host, network for feeds and config storage; common desktop/mobile browsers are clients. Hosting and third-party data APIs cost separately. Cached or unavailable sources can be stale; community widgets add their own dependencies. Not a reliable source of urgent alerts by itself.

### A small first step

15–25 minutes: inspect the official example YAML and documentation at https://github.com/glanceapp/glance . In a ready local instance use one calendar and two public RSS sources, limit visible entries and compare timestamps with originals. Skip private integrations and community widgets until the basic configuration is clear.
