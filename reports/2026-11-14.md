## 1. GitHub CLI

Inspect repository work without leaving the terminal.

### What it does

The official gh client brings issues, pull requests and other GitHub resources to command-line workflows. It supports GitHub.com and supported Enterprise services on Windows, macOS and Linux.

### Why we recommend it

Useful when you already work in a terminal and need to inspect remote work alongside local Git state. It complements Git rather than replacing version control.

### How it could help you

1. Read a public repository's pull-request status before reviewing local changes.
2. Inspect an issue's details and open its canonical page when more context is needed.

### Who it fits and what to expect

MIT client; requires network access and appropriate authentication for many operations. Enterprise accounts and hosted services have separate terms. No GPU needed. Permissions and selected account still matter; write commands can change remote state. It does not bypass repository access or rate limits.

### A small first step

15–25 minutes after setup: follow https://cli.github.com/manual/ and check gh auth status privately. Use read-only commands on a public repository, such as viewing repository metadata and listing a few issues. Confirm the target before trying any write operation; this report does not execute gh.

## 2. hyperfine

Compare command runtimes through repeated measurements.

### What it does

Provides repeated-run statistics, warmups, parameter scans and result export. Current README distinguishes directly executed commands from explicit shell interpretation via -S.

### Why we recommend it

Recommended when a concrete performance claim needs a small reproducible timing comparison. It measures a chosen workload; it cannot establish which implementation is correct or generally fastest.

### How it could help you

1. Compare two equivalent read-only transformations on the same tiny input.
2. Inspect how warmup affects a command that repeatedly reads a test file.

### Who it fits and what to expect

Apache-2.0 tool with cross-platform binaries. Needs the measured executables, CPU/time and any output storage; no GPU unless measured code needs one. Repeated commands repeat side effects. Background load, caches and different output semantics can invalidate comparisons. Avoid applying privileged cache-clearing examples casually.

### A small first step

20–30 minutes: follow the official README, select two harmless commands with checked equivalent results, set a small explicit run count and export JSON. Record OS, command versions, input and warmup policy. Compare variation as well as averages; no benchmark was executed for this report.

## 3. just

Save a small set of project tasks under readable recipe names.

### What it does

Stores recipes in a justfile, with arguments, recipe listing, shell selection and optional imports/modules. It is a command runner rather than a dependency-tracking build system.

### Why we recommend it

Useful when repeatable project commands are scattered through notes. A short recipe can make the intended invocation visible, without introducing a larger task framework.

### How it could help you

1. Give the existing documentation-preview command one memorable name.
2. List the project's validation commands for a collaborator before they run them.

### Who it fits and what to expect

CC0-1.0 project, with binaries for Windows, macOS and Linux. Recipes need their own tools and a compatible shell. On Windows use an available sh or explicitly configure PowerShell. No GPU needed for the runner. It does not make shell scripts portable automatically, and a justfile can execute arbitrary commands.

### A small first step

15–25 minutes: read https://just.systems/man/en/ and create a disposable justfile with one harmless print recipe and one version-check recipe. List recipes, run each and inspect the file before execution. Add an existing project command only after verifying its working directory and arguments.

## 4. Glow

Read local Markdown as a formatted document in the terminal.

### What it does

Renders Markdown in a command-line interface and can discover files in subdirectories or a local Git repository. The project supplies terminal UI and platform-specific packages/binaries.

### Why we recommend it

Recommended when a README or operational note should stay near your terminal session. It is a reader, so the source can remain in the existing editor and version-control workflow.

### How it could help you

1. Browse a small repository's Markdown instructions without a browser.
2. Review a local checklist while preparing a command sequence.

### Who it fits and what to expect

MIT reader with Windows, macOS, Linux and several Unix packages. Needs a compatible terminal, fonts and local files; no database or GPU. Terminal rendering differs from the final web/PDF destination, especially for wide tables, images or embedded HTML. It is not a substitute for checking a published page.

### A small first step

15–20 minutes: follow the official README, open a harmless local Markdown file with headings, a list and code block, then try directory discovery. Compare with the raw text and check whether the terminal width hides information. Do not treat this as a final website preview.

## 5. Atuin

Search recorded commands together with the context in which they ran.

### What it does

Stores terminal history in SQLite with fields such as working directory, exit status and duration. Current README also describes agent-session capture and optional end-to-end-encrypted synchronization.

### Why we recommend it

Useful when recalling the correct earlier command depends on where it ran or whether it succeeded. Start with limited local history rather than enabling every capture and sync integration.

### How it could help you

1. Find a successful prior test command within a project directory.
2. Recover the structure of a harmless earlier query, edit it and recheck its target before reuse.

### Who it fits and what to expect

MIT project with documented shell integrations including bash, zsh, fish and PowerShell; OS and shell setup must match current guidance. Local capture needs disk; optional sync/server services and hosting have separate requirements or terms. History may contain secrets or private paths despite filtering. Encryption is not a substitute for controlling capture and access.

### A small first step

20–30 minutes: follow https://docs.atuin.sh/ and inspect capture, exclusion and deletion settings first. In a disposable shell session, record only harmless test commands, search by context and edit a selected entry before reuse. Leave optional sync and agent capture disabled until their scope is understood.
