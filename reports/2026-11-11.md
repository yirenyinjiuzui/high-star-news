## Where to start today

## 1. Transformers

Load supported pretrained models through a common model-definition framework.

### What it does

Provides model definitions and high-level pipelines for text, vision, audio and multimodal inference and training. Tokenizers and preprocessing connect raw inputs to each model's expected representation.

### Why we recommend it

Useful when a task needs a known model and reproducible configuration. It exposes more modeling choices than a chat interface, but still requires selecting and evaluating an appropriate checkpoint.

### How it could help you

1. Compare a small text classifier's outputs on ten fabricated sentences.
2. Inspect a tokenizer's output before preparing inputs for a supported model.

### Who it fits and what to expect

Apache-2.0 library; current README specifies Python 3.11+ and PyTorch 2.6+. Compatible environments exist on major desktop OSs, but accelerators and packages vary. Model downloads consume disk; RAM/VRAM depends on model and task. Model licenses, gated access and cloud compute are separate. Not a guarantee of factual answers or suitability; remote model code deserves explicit review.

### A small first step

20–30 minutes: follow https://huggingface.co/docs/transformers/pipeline_tutorial and first inspect a small model card, license and download size. If an environment is ready, try a small task on fabricated inputs and record model/revision/settings. Otherwise spend the session assessing requirements, without downloading a large checkpoint.

## 2. Datasets

Load and transform examples with explicit, reusable preprocessing steps.

### What it does

Loads public datasets or local files and supports map-based preprocessing, caching, Arrow-backed storage and streaming. Optional dependencies enable different media formats and framework integrations.

### Why we recommend it

Recommended when dataset preparation needs to be repeatable rather than a sequence of manual edits. Inspecting features and a tiny subset first can expose schema assumptions.

### How it could help you

1. Load a local fabricated JSONL file and add a text-length column.
2. Inspect a small public dataset subset and compare its documented split definitions before use.

### Who it fits and what to expect

Apache-2.0 library for compatible Python environments on major OSs; CPU, disk/cache and network depend on input. Media extras add dependencies; no GPU is needed for a small text example. Dataset licenses are independent. Streaming still transfers data and does not make every operation available or free of memory limits. Cache reuse does not prove data quality or split validity.

### A small first step

15–25 minutes: follow https://huggingface.co/docs/datasets/ using five local fabricated JSONL records. Load them, inspect features, map one derived field and verify every result. Before trying a Hub dataset, read its card, license and split provenance; do not download a full large corpus for the first attempt.

## 3. llama.cpp

Run supported language models through a C/C++ inference stack.

### What it does

Provides local inference tools, a compatible API server, quantized-model support and CPU/GPU backends. CPU and GPU execution can be combined, depending on build and supported model.

### Why we recommend it

Consider it to understand local inference requirements and control an actual model file. It is a lower-level option than a packaged chat application; quantization trades memory and other behavior that must be evaluated.

### How it could help you

1. Compare a small quantized model's responses on a fixed set of harmless prompts.
2. Explore a local API server as the backend for an existing test UI.

### Who it fits and what to expect

MIT engine with Windows, macOS and Linux build/binary options. Requires supported weights, disk, RAM and compatible backend libraries; GPU acceleration is optional, not universal. Model licenses are separate. No cloud API credits are included. Unsupported architectures or excessive context can fail or exhaust memory, and local output can still be wrong.

### A small first step

20–30 minutes: read the official README and build/backend guide, compare one small GGUF model's size with available memory, and inspect its license. If already installed with suitable weights, run a short prompt locally and record settings. Otherwise stop at a resource plan; this report did not run a model.

## 4. vLLM

Serve supported models with request scheduling and memory-management features.

### What it does

An inference and serving engine with continuous batching, PagedAttention, caching, quantization options and compatible API endpoints. Supported backends and model architectures vary, with plugins for some hardware.

### Why we recommend it

Recommended when serving several requests is an actual requirement. It offers scheduling infrastructure; any throughput advantage must be measured with the intended model, hardware and workload.

### How it could help you

1. Plan a controlled comparison of single-request latency and concurrent-request throughput.
2. Expose an already validated model behind a test client while observing resource use.

### Who it fits and what to expect

Apache-2.0 software; choose a documented OS/backend/hardware combination rather than assuming a generic desktop install works. Model weights, driver stack, RAM/VRAM and compilation caches can be substantial. GPU/cloud costs and model terms are separate. Not the simplest first local-chat option. Batching can change latency, and unsupported kernels/models can block setup.

### A small first step

20–30 minutes: review https://docs.vllm.ai/en/latest/getting_started/ and supported models. Write down model, backend, available memory and a tiny request budget. If a ready test deployment exists, inspect its configuration; otherwise do not provision paid compute merely to finish the exercise. No serving benchmark was executed here.

## 5. ONNX Runtime

Execute a supported exported model through a cross-platform runtime.

### What it does

Runs machine-learning models with graph optimizations and execution providers for different hardware. The repository covers inference and training; this recommendation focuses on inference of an already exported model.

### Why we recommend it

Useful when deployment should be decoupled from a training framework. Conversion and execution are separate stages: verify numerical agreement before assessing speed.

### How it could help you

1. Run a small public ONNX sample and inspect input/output names and shapes.
2. Compare a converted model's outputs against its original framework on the same test inputs.

### Who it fits and what to expect

MIT runtime with platform-specific packages and providers, including major desktop environments. Needs a compatible model/opset, CPU or supported accelerator and provider dependencies. Optional GPU drivers and cloud resources cost separately. Not every operation exports or runs on every provider. README notes possible telemetry; review privacy settings. No speedup is guaranteed.

### A small first step

20–30 minutes: follow https://onnxruntime.ai/docs/ and choose a tiny official inference example. Inspect model inputs, shapes, opset and provider requirements first. In an existing environment compare a few outputs against reference results; otherwise record conversion/installation requirements before trying a large model.
