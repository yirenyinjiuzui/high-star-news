## Where to start today

For repeated work across apps, start with n8n and a manual workflow that uses sample data. For a first local-model experiment, choose Ollama; for audio-to-text, choose whisper.cpp instead. Langflow helps you understand and prototype an AI pipeline visually, while LiteLLM is worth considering once you actually need more than one model provider. You do not need to deploy all five together.

## 1. n8n

Connect triggers, data transformations, app actions, and optional AI steps on a visual canvas.

### What it does

n8n builds workflows from connected nodes, with conditions, integrations, and custom JavaScript or Python where supported. Its official README describes self-hosting or cloud use, model-provider connections, and human approval steps. This is a workflow service that you configure and operate; it does not automatically discover safe automations for your accounts.

### Why we recommend it

Recommended to make a recurring process explicit: what starts it, which fields move between apps, and where a person should review the result. It is most useful when the same structured task happens repeatedly. Start without AI if ordinary rules can do the job, and add a model only for a step that needs interpretation.

### How it could help you

1. Prepare a draft weekly reading digest from a small sample list: transform titles and links, filter a chosen category, and inspect the resulting text before connecting a publishing destination.
2. Convert a test form payload into a normalized task record, branch on missing fields, and route incomplete records to review rather than silently creating bad entries.

### Who it fits and what to expect

Fits someone willing to learn credentials, workflow logic, and service maintenance; less suitable for a one-off copy/paste task or someone expecting zero setup. The editor runs in a browser; self-hosting needs a running host, persistent storage, and, for the documented Docker route, Docker. Cloud, enterprise features, external APIs, and hosting can cost money. n8n is source-available fair-code under Sustainable Use and Enterprise licenses, not an unrestricted MIT-style project. The root license limits ordinary use to internal business or personal/non-commercial purposes and treats redistribution and enterprise files separately. Check the official license before offering a hosted product to others. Retries or repeated triggers can repeat external actions; review behavior before enabling unattended writes.

### A small first step

15–30 minutes after setup: follow the official README's Docker instructions or use a cloud trial if available, create Manual Trigger → sample data transformation → conditional branch, and inspect both branches. Keep it manual and disconnected from real write destinations until the output is correct. License source: https://github.com/n8n-io/n8n/blob/master/LICENSE.md .

## 2. Langflow

Build and inspect AI workflows visually, then expose them through APIs or MCP.

### What it does

Langflow connects model, prompt, retrieval, and tool components in a visual editor. Its playground supports step-by-step experimentation, Python components can be customized, and workflows can be exported as JSON or served through built-in API and MCP interfaces. It helps assemble an application pipeline; choosing good sources and evaluating the generated answers remain your work.

### Why we recommend it

Recommended for learning what happens between an input and an AI answer. Seeing each component can make it easier to isolate a bad prompt, missing retrieval result, or wrong model configuration than starting with a large opaque assistant. It also offers a path from a prototype to a callable flow, without implying that the prototype is ready for production.

### How it could help you

1. Create a small question-answering experiment over two non-sensitive notes, then ask one question the notes answer and one they do not; inspect retrieved context and whether the answer admits missing evidence.
2. Make a reusable text-classification flow with fixed labels, test ten sample inputs in the playground, and export the flow definition for review before connecting another application.

### Who it fits and what to expect

Fits curious builders who can configure a model and understand inputs/outputs; less useful for someone who only wants a finished chat application. Desktop packages are available for Windows and macOS; Python and Docker routes support other suitable environments. The current README lists Python 3.10–3.14 for the package route. Repository code is MIT licensed, but model APIs, vector storage, cloud hosting, and hardware are separate costs. Local models need their own resources. Use authentication for a server, and keep provider keys out of exported or shared examples. Retrieval can omit relevant passages and models can invent answers; visual wiring is not an accuracy guarantee.

### A small first step

15–30 minutes after installation: use the Desktop option or follow the current package quickstart at https://github.com/langflow-ai/langflow#readme . Start with input → prompt → one configured model → output, run three ordinary and two ambiguous inputs, then export the JSON. If using an official server package, follow the README's password/authentication setup rather than copying old auto-login tutorials.

## 3. Ollama

Run supported language models locally and make them available through a command line or HTTP API.

### What it does

Ollama downloads and runs supported models, offers interactive chat, and serves model-management and inference APIs. Official Python and JavaScript libraries can call the runtime. The README also describes cloud models and application integrations; local execution and a cloud-backed session are different operating choices.

### Why we recommend it

Recommended to test whether a local model is useful on hardware you already own before building a larger AI stack. It can provide one model endpoint for multiple experiments. The point is control over model choice and execution location, not a promise that a laptop will match a hosted model's speed or answer quality.

### How it could help you

1. Try rewriting a short, non-sensitive draft with a small local model and compare the result against the original for missing facts, awkward wording, and measured wait time.
2. Point a small test script at the local chat API and classify ten sample notes into a fixed set of categories, keeping expected answers so you can judge whether local inference is sufficient.

### Who it fits and what to expect

Fits someone prepared to download model files and check RAM/VRAM; less suitable if storage is tight or you need guaranteed low-latency answers without hardware planning. Installers support Windows, macOS, and Linux, with Docker also documented. The runtime is MIT licensed; model weights have their own licenses, and cloud access may involve plans or usage charges. Local execution still uses storage, memory, compute, and electricity. Requirements depend on model size, quantization, and context length; there is no universal minimum that makes every model work. A locally running model does not make a connected app's plugins, logs, or cloud calls local. Generated facts still need verification.

### A small first step

15–30 minutes: inspect the official model library and your available disk/RAM, then choose one small supported model whose license fits your use. Follow the README installation route and run `ollama run <model-name>` with the selected real name. Ask the same three short prompts and record accuracy and wait time. Confirm you selected a local model rather than a cloud entry. Downloads may exceed the trial window.

## 4. whisper.cpp

Transcribe audio on your own device using a C/C++ implementation of Whisper inference.

### What it does

whisper.cpp runs Whisper speech recognition with CPU-only and several hardware-accelerated backends. The repository includes command-line transcription, an HTTP server example, streaming examples, quantization, and voice-activity detection. It performs inference rather than training. With a compatible model already downloaded, supported workflows can process audio without sending it to a transcription service.

### Why we recommend it

Recommended when you want searchable text from recordings and can tolerate setup and proofreading. It provides a concrete local alternative to paying for each transcription request, while leaving hardware time and review effort visible. It is not a finished meeting-management product or a guarantee of accurate speaker names.

### How it could help you

1. Turn a two-minute recording of your own spoken study notes into a draft transcript, then correct names and technical terms while listening to the audio.
2. Create draft captions for a short video you are allowed to process, inspect timestamps and omissions, and revise the transcript before sharing it.

### Who it fits and what to expect

Fits users comfortable with a CLI or developers embedding speech recognition; less suitable for someone expecting a polished recorder with no setup or an unreviewed verbatim transcript. Windows, macOS, Linux, mobile examples, and WebAssembly are documented. Code is MIT licensed; obtain model files and check their own terms. A compiler/CMake or an appropriate prebuilt route, model storage, and CPU/GPU resources are needed. The official table gives base roughly 142 MiB on disk and about 388 MB memory, and large roughly 2.9 GiB and about 3.9 GB; actual backend/runtime use can differ. Noise, overlapping voices, language choice, and silence can cause mistakes or invented text. The documented CLI expects 16-bit WAV input.

### A small first step

15–30 minutes if build tools are ready: follow the official quickstart, choose tiny/base for a short trial, and run the CLI on the included sample before a one-minute personal recording converted to 16 kHz mono PCM 16-bit WAV. For Chinese, use a multilingual model rather than a `.en` variant. Compare every line with the audio; stop the trial at setup verification if downloading or compilation takes longer.

## 5. LiteLLM

Use a common interface for model providers, either in a Python SDK or through a shared gateway.

### What it does

LiteLLM maps requests to many model providers using a common API format. The Python SDK supports direct integration; the proxy adds a central endpoint with routing, virtual keys, spend tracking, and management features. Provider support varies by endpoint and model, so a familiar request shape does not imply identical tool calling, output, or errors everywhere.

### Why we recommend it

Recommended when a real application already needs multiple providers, controlled fallback, or a place to observe model spending. It can reduce repeated integration work and centralize configuration. For a single small script with one provider, the original provider SDK may be simpler; do not add a gateway just because it is popular.

### How it could help you

1. Send the same ten non-sensitive classification examples through two supported models using one calling interface, then compare label accuracy, latency, and reported usage before choosing a default.
2. Give two test applications separate virtual keys through a local gateway so usage can be attributed separately, and inspect how a deliberately failed request is reported before enabling fallback.

### Who it fits and what to expect

Fits developers and service operators who can manage provider credentials, request semantics, and deployment; not a consumer chat app. A supported Python environment is enough for SDK experiments; a shared proxy needs a running host and may need persistent database configuration for management features. The root LICENSE grants MIT terms outside `enterprise/`; that directory uses separate terms. Hosted and enterprise services, provider tokens, hosting, and storage can cost money. Fallback may create extra billable requests and must respect data-location requirements; gateway logs can contain prompts. Usage and cost tracking depend on provider data and configuration, so inspect actual billing rather than treating a dashboard as a guaranteed spending cap.

### A small first step

15–30 minutes: follow the Python SDK section in the official README in a fresh environment, use one provider key from an environment variable, and make one short non-sensitive completion with an explicit small output limit. Save the response, usage fields, and error behavior before trying a second provider. Choose the regular SDK distribution for this trial; the README warns not to install overlapping `litellm` and `litellm-core` distributions together. License: https://github.com/BerriAI/litellm/blob/main/LICENSE .
