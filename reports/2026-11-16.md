## 1. Datasette

Explore a small database through a browser and an accompanying API.

### What it does

Publishes data as an interactive website/API. Basic use serves a SQLite database locally, and metadata can describe source and license. A separate browser-based Datasette Lite option is linked by the project.

### Why we recommend it

Useful when someone needs to inspect records without installing a database GUI. A tiny public or fabricated database is a clearer starting point than publishing a real working dataset.

### How it could help you

1. Browse a fabricated catalog and filter for one category.
2. Attach source/license metadata to a public data snapshot before sharing it.

### Who it fits and what to expect

Apache-2.0 library; README requires Python 3.11+, with compatible desktop/server environments and Docker options. Needs a database, CPU/RAM and storage; hosting costs separately, no GPU needed. Serving data is not automatically anonymization or permission management. Database contents and metadata need review before exposure.

### A small first step

15–25 minutes: follow https://docs.datasette.io/ using a tiny fabricated SQLite file in a local-only session. Browse two tables, inspect a JSON response and verify counts. Read deployment/access guidance before publishing; do not point the first test at private browser history or a production database.

## 2. SQLFluff

Check SQL against an explicit dialect and a selected rule set.

### What it does

A configurable SQL linter with dialect and templating support, including Jinja and optional dbt integration. It can report issues or apply supported fixes; dialect coverage is not necessarily complete.

### Why we recommend it

Recommended when SQL style and small static issues repeatedly distract from review. It checks configured rules rather than validating query intent or result correctness.

### How it could help you

1. Report layout issues in a small query before code review.
2. Compare lint output under the correct dialect with a deliberately mismatched one.

### Who it fits and what to expect

MIT Python tool for compatible Windows, macOS and Linux environments. Needs package dependencies, with extras for some templaters; ordinary linting needs no GPU. Templating plugins may access project context or services. Fixes change files, and a clean lint result does not establish schema validity, efficient execution or correct joins.

### A small first step

15–20 minutes: follow https://docs.sqlfluff.com/ on a disposable .sql file with known dialect. Run lint first, read one diagnostic, fix it manually and inspect the diff. Do not run bulk fixes over an existing project during the first trial.

## 3. Apache Superset

Explore existing SQL data and assemble charts in a web application.

### What it does

A business-intelligence platform with chart building, a SQL editor, dimensions/metrics, caching and role/authentication options. Data connections depend on supported drivers and dialects.

### Why we recommend it

Useful when multiple readers need interactive exploration over an existing data source. It offers a shared UI, but consistent metric definitions and operational administration remain necessary.

### How it could help you

1. Compare a chart's grouped totals with a read-only SQL query.
2. Build a sample dashboard from a small non-sensitive dataset and inspect its filters.

### Who it fits and what to expect

Apache-2.0 application; requires a supported server/container stack, metadata storage, database drivers and browser clients. Query/storage/hosting costs are separate; no GPU required. More demanding than a static chart file. Database permissions, authentication and updates need active management, and cached results can be stale.

### A small first step

20–30 minutes: read https://superset.apache.org/user-docs/ and administrator requirements. If a ready authorized demo instance exists, inspect sample charts and change a filter, checking the underlying definition. Otherwise plan a minimal test deployment rather than assuming a full installation fits this session.

## 4. Metabase

Give readers a question-and-dashboard interface over connected data.

### What it does

Offers visual questions, a SQL editor and interactive dashboards. The repository also describes advanced capabilities whose availability depends on edition; it contains both open-source and commercial source.

### Why we recommend it

Recommended when non-SQL collaborators should inspect a defined dataset. Evaluate a few known questions before deciding whether a shared server and edition-specific features are justified.

### How it could help you

1. Create a sample category-count question and compare it with known totals.
2. Add a dashboard filter and check that every included chart responds as intended.

### Who it fits and what to expect

Open-source edition is AGPL; commercial editions have a separate Metabase license. Hosting/cloud, database resources and some features cost separately. Self-hosting needs the documented runtime/container, application storage, backups and browser clients. No GPU required for basic dashboards. A chart is not proof of data quality; broad database access and feature assumptions need review.

### A small first step

20–30 minutes: use the official tour at https://www.metabase.com/learn/metabase-basics/overview/tour-of-metabase . In an existing authorized test instance, use sample data for one question and filter. Check which edition provides each desired feature before connecting real data or starting a paid trial.

## 5. Evidence

Combine SQL and Markdown into a reviewable report project.

### What it does

A code-based reporting tool using SQL and Markdown, with local development and self-hosted static output or hosted publishing options. Current README supplies CLI installation guidance for major platforms.

### Why we recommend it

Included below 10,000 stars because narrative reporting in source files is a distinct alternative to drag-and-drop dashboards. Recent activity supports this explicit exception, not a claim that stars prove quality.

### How it could help you

1. Put a small query's explanation beside its report output.
2. Review a metric-definition change as a source diff before republishing.

### Who it fits and what to expect

MIT project; current CLI documentation covers Windows, macOS and Linux. Needs the documented development environment and data connectors, plus disk for outputs. Hosted plans, database queries and optional AI/agent tools have separate terms/costs. Static output can embed data, so publishing is an intentional data-sharing decision. It does not make a query correct.

### A small first step

20–30 minutes: read https://docs.evidence.studio and create a disposable project only if the environment is ready. Use fabricated data and a single SQL/Markdown report, preview locally and inspect generated content. Otherwise compare CLI/connector requirements; do not publish or connect a production database for the first test.
