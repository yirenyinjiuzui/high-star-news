## Where to start today

For a checkout form, start with the question you need answered. Vitest can check the total. React Testing Library can check the validation message. MSW can supply a failed payment response. Storybook can isolate the error panel for review. Playwright can follow the shopper from the cart to the confirmation screen.

## 1. Playwright

Check whether a whole task works in a real browser.

### What it does

Playwright Test opens pages in Chromium, Firefox or WebKit. Locators select controls by role and name, and assertions can wait for the expected page state.

### Why we recommend it

Choose it when a failure can occur between screens, such as a filter disappearing after navigation.

### How it could help you

1. Check that a selected filter survives opening a detail page and going back.
2. Verify that a keyboard user can open a dialog and return focus to its trigger.

### Who it fits and what to expect

Apache-2.0. The Node.js runner supports specified Windows, macOS and Linux versions. Budget disk space for browser binaries and time to start the app. Small arithmetic checks are cheaper to exercise directly.

### A small first step

Allow 25–30 minutes on a supported machine. Point the starter test at a local demo, click a named link and assert the destination heading. Run once in Chromium, then run the same assertion in Firefox.

## 2. Storybook

Give a hard-to-reach interface state its own preview.

### What it does

A story renders a component with named inputs. Save several stories for one component and switch between them in the browser.

### Why we recommend it

It gives designers and developers a repeatable way to discuss a single state without navigating an entire application.

### How it could help you

1. Compare a short button label with a long translation in a narrow container.
2. Review the empty state of a list before its data service is ready.

### Who it fits and what to expect

MIT-licensed core runs locally with a supported framework integration, Node.js and a browser. Hosted visual testing may cost extra. Stories need the same theme or providers as the real component to give a faithful preview.

### A small first step

Allow 20 minutes in a configured project. Add two stories for the same button, changing only the label. Narrow the preview and record the first width at which either label clips.

## 3. Vitest

Check a rule with small inputs and explicit expected results.

### What it does

Vitest runs test files, supports watch mode and can share Vite configuration with an application. Its assertions suit functions with deterministic outputs.

### Why we recommend it

A small failing case can tell you exactly which boundary input broke after an edit.

### How it could help you

1. Check whether a zero-item cart displays the correct total.
2. Pin down how a slug formatter handles repeated spaces.

### Who it fits and what to expect

MIT-licensed Node.js tool. Match the runner to the supported Vite and Node versions. The default Node environment is enough for pure functions. Layout and browser-specific behavior require a suitable browser environment.

### A small first step

Allow 15 minutes. Pick one formatter, write cases for an ordinary string and an empty string, then run Vitest in watch mode. Change one expected value and check that the failure identifies that case.

## 4. React Testing Library

Test the controls and messages a user can find on screen.

### What it does

Render a React component into a DOM and query the output by accessible role, name or label. After an interaction, assert that the visible result has changed.

### Why we recommend it

A test written against a named control can survive a refactor that changes internal component state but preserves behavior.

### How it could help you

1. Submit an empty form and find the validation message.
2. Toggle a disclosure button and check that its details become available.

### Who it fits and what to expect

MIT-licensed helpers require React, a separate test runner and a DOM environment such as jsdom or a browser. They suit behavior checks. A simulated DOM cannot confirm that text fits on screen.

### A small first step

Allow 20 minutes in a React test project. Render a collapsed disclosure, query its button by role and name, click it and look for the details. Rename an internal state variable and rerun the test.

## 5. Mock Service Worker (MSW)

Give the same screen predictable success and error responses.

### What it does

Request handlers describe responses at the network boundary. Browser development uses a service worker, while Node.js tests can reuse handlers through the Node integration.

### Why we recommend it

Use it when an unusual response is difficult to produce reliably against a shared development server.

### How it could help you

1. Show an empty search result without modifying shared records.
2. Return a temporary server error and check that the retry control appears.

### Who it fits and what to expect

MIT-licensed library for supported browsers and Node.js. Local examples need no paid backend. The browser worker must be registered within the correct scope. Simulated responses can drift from the real API contract.

### A small first step

Allow 20–30 minutes with a local demo. Give its list request a handler returning an empty array, then switch that handler to a 503 response. Verify that the page shows different empty and error states.
